SecureLink Validator Pro — The Trap in the Links

Blind SSRF in a URL validator, escalated via Gopher into an unauthenticated internal Redis.

Target 34.0.219.143:5030 Chain SSRF → Gopher → Redis Difficulty Medium

01Recon & the filter

A URL-verification service fetches a user-supplied URL server-side — a classic SSRF surface. Pointing it inward at http://127.0.0.1 is blocked:

The Network → Response body reveals the reasoning:

{
  "error": "Invalid or blocked URL detected",
  "message": "URL contains blocked patterns or invalid protocol",
  "note": "Localhost and private IP ranges are not allowed"
}
Key insight
"blocked patterns" → the filter matches text, not the resolved IP. A string blacklist can be fooled by spelling the same address differently.

03Bypassing the filter

The lazy bouncer. He has a banned-names list and only checks the name you say, letter for letter — never your face. Say "Jonathan Smith" (on the list) → rejected. Say "J. Smith" (not literally listed) → admitted — same person. The address didn't change, only its spelling. That's 127.0.0.1 vs 127.1.

An IPv4 is really one 32-bit number; the parser accepts shorthand where the last part fills the missing octets. Same loopback, different text:

FormReads asFilter
127.0.0.1canonical✗ blocked
127.1→ 127.0.0.1✓ passed
2130706433decimal of the IP✓ passed
0x7f000001hex of the IP✓ passed

All three passing proves the filter did no host normalization — a real resolver would have caught them all.

04Gopher → Redis

HTTP can't issue Redis commands; gopher:// sends raw bytes ("raw TCP in a URL"), which is why a hardened validator should forbid it. Redis speaks RESP, each line ending in \r\n, URL-encoded as %0d%0a:

# PING → RESP *1 $4 PING
gopher://127.1:6379/_%2a1%0d%0a%244%0d%0aPING%0d%0a
# → +PONG  (channel confirmed)

05Enumeration

Standard sequence: INFO → KEYS * → GET. INFO keyspace showed db0:keys=44; KEYS * listed them:

Why GET
Redis is a key→value store: KEYS lists names, GET returns a single key's value. RESP even gives each key's length ($20) — the exact number to reuse in the payload.
# GET the target key → RESP *2 $3 GET $20 <key>
gopher://127.1:6379/_%2a2%0d%0a%243%0d%0aGET%0d%0a...

06How I got there

  1. URL validator → think SSRF. Aim it inward at 127.0.0.1.
  2. Read the error. "patterns" = text filter → beatable with alternative spellings.
  3. Read page source. Debug routes leaked Redis, gopher, no-auth.
  4. Re-encode loopback. 127.1 passes → now reaching the server.
  5. Switch to gopher. Speak RESP; PING → +PONG confirms it.
  6. Let Redis guide you. Each error (-ERR *1, empty *0) pointed to the next fix → INFO/KEYS/GET.

07Remediation

String blacklistResolve host server-side, reject loopback/private ranges — never match raw text.
Gopher allowedWhitelist http/https only.
Open RedisSet requirepass, bind localhost, rename risky commands.
Public debug routesRemove /debug/health & /api/docs in production.
